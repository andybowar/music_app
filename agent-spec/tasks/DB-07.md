# DB-07 · User access status (approval) migration


**Goal.** Every account has an access status, and only approved accounts can reach any data.

## Read first
- `agent-spec/AGENTS.md`
- `agent-spec/SPEC.md` (REQ-AUTH-03, REQ-AUTH-08, and §6 "Do SSO users whose group maps to a branch skip approval?")
- `agent-spec/contracts/schema.md` (`access_status` enum and `users` columns)
- `agent-spec/contracts/types.md` (`ACCESS_STATUSES`, `AppUser.accessStatus`)
- `agent-spec/contracts/permissions.md` (pending/rejected users can do nothing; RLS helper SQL)
- `agent-spec/change-requests/OWNER-access-approval.md`
- `db/migrations/0003_rls.sql` (DB-03), especially `app_user_role()`, `app_user_branch()` and the `users_select` policy
- `agent-spec/change-requests/DB-01-migrate-scripts.md` (create the file with `pnpm db:generate --custom --name access_status`)

## Requirements
- `REQ-AUTH-03` — Anyone can request an account; new accounts start pending and can see no data until an admin approves them. Invited accounts are approved when created.
- `REQ-AUTH-08` — Admins approve or reject pending accounts; pending and rejected users see only an account-status page.

## Deliverables
- [ ] `0004_access_status.sql`: `access_status` enum; `users.access_status` (default `'pending'`), `access_decided_by`, `access_decided_at`; every existing row backfilled to `'approved'`
- [ ] `app_user_role()` and `app_user_branch()` return null unless `access_status = 'approved'`, so every existing RLS policy denies pending and rejected users
- [ ] `users_select` still lets a pending or rejected (but not disabled) user read their own row
- [ ] Drizzle schema (`db/schema/users.ts`, `enums.ts`) and the drizzle `meta/` journal and snapshot updated (touches)
- [ ] `types/domain.ts` (`ACCESS_STATUSES`, `AccessStatus`, `AppUser.accessStatus`) and `types/validation.ts` (`appUserSchema`) updated to the contract (touches)
- [ ] `fixtures/users.json`: existing users `approved`; add one `pending` and one `rejected` user (touch)
- [ ] Seed (`db/seed/`) writes each user's `access_status` from the fixtures (touch)

## Acceptance criteria
- [ ] Integration tests: a pending and a rejected user get no rows from songs, lists, themes and the rest; each can read only their own `users` row; an approved user is unaffected; a disabled user still gets nothing
- [ ] Fresh `db:reset && db:migrate && seed` and a second `db:migrate` (no-op) both succeed; the existing `tests/db/` suites still pass
- [ ] Definition of Done in `AGENTS.md` §5 is satisfied
